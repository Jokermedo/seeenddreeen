# خطة الصيانة والاستقرار والتحسين الشاملة

**اسم المشروع:** Sendreen Store  
**تاريخ الإصدار:** 2026-04-12  
**حالة المستند:** معتمد كمرجع العمل الأساسي للصيانة والتحسين  
**النطاق:** التطبيق، البنية، الجودة، الاختبارات، النشر، التوثيق، إدارة التغيير

## 1. الملخص التنفيذي

المشروع يعمل حاليًا من ناحية التشغيل الأساسية، حيث يمر عبر `lint` و`build` والاختبارات، لكنه ما زال يحمل دينًا تقنيًا واضحًا في التنظيم والبنية والتوثيق. المشكلة الحالية ليست "تعطل كامل"، بل "قابلية صيانة منخفضة" قد تتحول سريعًا إلى أخطاء وظيفية وتباطؤ في التطوير إذا استمر العمل بنفس النمط.

أبرز ملامح الوضع الحالي:

- التطبيق مبني على `Next.js 16` و`React 19` و`TypeScript`.
- الوظيفة الأساسية للطلب تعمل، مع تكامل واتساب ورفع صور إلى Cloudinary.
- توجد ملفات كبيرة جدًا ومركبة، أهمها [app/page.tsx](/d:/New%20folder%20(2)/sendreen-store/app/page.tsx) و[app/globals.css](/d:/New%20folder%20(2)/sendreen-store/app/globals.css).
- يوجد تكرار في أنماط CSS وخلط بين توثيق قديم ووضع فعلي أحدث.
- كان المشروع يحتوي سكربتات صيانة غير متوافقة مع بيئة PowerShell/Windows، وتم استبدالها بسكربتات Node متعددة المنصات.
- تم تنفيذ تحسينات سريعة مهمة بالفعل قبل إصدار هذا المستند:
  - إضافة [lib/order.ts](/d:/New%20folder%20(2)/sendreen-store/lib/order.ts) لفصل منطق إنشاء رقم الطلب وتطبيع رقم واتساب.
  - تشديد تحقق رفع الملفات في [lib/utils.ts](/d:/New%20folder%20(2)/sendreen-store/lib/utils.ts).
  - رفع جودة الاختبارات عبر [lib/actions.test.ts](/d:/New%20folder%20(2)/sendreen-store/lib/actions.test.ts) و[lib/order.test.ts](/d:/New%20folder%20(2)/sendreen-store/lib/order.test.ts).
  - تحويل سكربتات التنظيف والتقرير إلى [scripts/clean.mjs](/d:/New%20folder%20(2)/sendreen-store/scripts/clean.mjs) و[scripts/quality-report.mjs](/d:/New%20folder%20(2)/sendreen-store/scripts/quality-report.mjs).

الهدف من هذه الخطة هو استعادة الاستقرار، رفع الجودة، تقليل التكرار، ووضع نظام صيانة مستدام يمنع تكرار الفوضى الحالية.

## 2. توصيف الوضع الحالي

### 2.1 البنية الحالية

- الواجهة الأساسية متمركزة بشكل كبير داخل ملف واحد: [app/page.tsx](/d:/New%20folder%20(2)/sendreen-store/app/page.tsx).
- الأنماط العامة تدار من [app/globals.css](/d:/New%20folder%20(2)/sendreen-store/app/globals.css) وفيه حجم كبير وتكرارات/دعم legacy.
- المنطق المساعد موجود في `lib/` لكنه ما زال يحتاج مزيدًا من التفكيك حسب المسؤوليات.
- التوثيق موجود في `docs/` لكنه غير موحد ويحتوي ادعاءات أو حالات لم تعد تمثل الوضع بدقة كاملة.

### 2.2 مؤشرات الجودة الحالية

- البناء الإنتاجي ناجح.
- ESLint ناجح.
- الاختبارات ناجحة.
- التغطية أصبحت مضبوطة بعتبات في Jest.
- لا توجد ثغرات `npm audit` ظاهرة عند الفحص الأخير.

### 2.3 مؤشرات الدين التقني

- ملف صفحة رئيسي ضخم جدًا ومركب.
- ملف CSS عام طويل ويحتوي فئات legacy متداخلة مع الفئات الحالية.
- منطق الواجهة، البيانات الثابتة، ونصوص المحتوى متشابكة داخل نفس الملف.
- التوثيق موزع على عدة ملفات بدون "مصدر حقيقة" واحد.
- لا يوجد تقسيم واضح للمسؤوليات على مستوى المكونات والخدمات.

## 3. قائمة المشاكل حسب الأولوية

### 3.1 أولويات حرجة `P1`

#### مشاكل وظيفية

- كان تطبيع رقم واتساب الإداري غير موثوق في بعض صيغ الإدخال المحلية المصرية.
- التحقق من ملفات الدفع قبل الرفع لم يكن صارمًا بما يكفي من ناحية النوع والحجم.

#### مشاكل بنيوية

- [app/page.tsx](/d:/New%20folder%20(2)/sendreen-store/app/page.tsx) نقطة اختناق رئيسية بسبب كبر الحجم وتعدد المسؤوليات.
- عدم فصل واضح بين:
  - عرض الصفحة
  - منطق الخطوات
  - نصوص المحتوى
  - مكونات FAQ/Testimonial
  - منطق الرفع والإرسال

#### مشاكل تشغيلية

- سكربتات الصيانة السابقة كانت مبنية على Bash وغير مناسبة للبيئة الحالية Windows/PowerShell.

### 3.2 أولويات عالية `P2`

#### تكرارات كود

- تكرار في أنماط CSS بين `.classic-*` و`.premium-*` و`.form-*`.
- تكرار أنماط مكونات/أجزاء واجهة داخل الصفحة الرئيسية.

#### مشاكل توثيق

- ملفات `docs/` الحالية ليست موحدة.
- بعض التوثيق يعلن الجاهزية الكاملة بينما لا يزال هناك دين تقني واضح.

#### مشاكل جودة

- لا توجد سياسة موحدة لحجم الملفات أو الحد الأعلى لتعقيد المكونات.
- لا يوجد تعريف رسمي لمعايير القبول الخاصة بالمراجعة والدمج.

### 3.3 أولويات متوسطة `P3`

#### مشاكل أداء وصيانة

- محتوى الصفحة كبير ومحمّل بنصوص ثابتة كثيرة داخل المكون نفسه.
- عدم وجود تقسيم للمحتوى الثابت في ملفات بيانات مستقلة.

#### مشاكل اتساق

- خلط بين أسماء كلاسات وأنماط قديمة وحديثة.
- التسمية ليست موحدة بالكامل بين الملفات، السكربتات، والتوثيق.

## 4. تحليل الجذر للأسباب

## 4.1 أسباب تقنية

- تسريع التسليم على حساب فصل المسؤوليات.
- تركيز الواجهة الكاملة في ملف واحد.
- غياب حدود صارمة للحجم، التعقيد، والتغطية منذ البداية.
- عدم وجود طبقة خدمات واضحة للتعامل مع الطلبات والدمج الخارجي.
- تراكم تكرارات CSS كحل سريع للحفاظ على التوافق الخلفي بدل إعادة تنظيم الأنماط.

## 4.2 أسباب بشرية

- اتخاذ قرارات قصيرة المدى لتسريع الإنجاز.
- غياب مراجعة بنيوية منتظمة للكود.
- عدم وجود تعريف مشترك لما يعتبر "جاهزًا" أو "مستقرًا".
- الاعتماد على الفحص البصري والتجربة اليدوية أكثر من الاختبارات المنظمة.

## 4.3 أسباب بيئية وتشغيلية

- العمل في بيئة Windows بينما كانت بعض السكربتات مكتوبة لمنصات Unix.
- وجود ملفات تشغيل/مخرجات (`.next`, `coverage`) يؤثر على القراءة إن لم يتم تنظيفها باستمرار.
- غياب مستودع Git مهيأ داخل هذا المجلد في وقت الفحص قلل من وضوح تاريخ التغييرات والمسؤولية.

## 7. توحيد الأساليب والاعتماديات

### 7.1 قواعد الكود

- لا يزيد أي مكون واجهة عن `200` سطر.
- لا يزيد أي ملف منطق عن `150` سطر دون مبرر.
- لا يتم وضع بيانات محتوى كبيرة داخل المكونات.
- أي سلوك له أثر وظيفي يجب أن يكون قابلًا للاختبار.

### 7.2 قواعد التسمية

- المكونات: `PascalCase`
- الدوال المساعدة: `camelCase`
- الثوابت العامة: `UPPER_SNAKE_CASE`
- الملفات التوضيحية/المحتوى: أسماء دلالية حسب المجال

### 7.3 الاعتماديات

- عدم إضافة مكتبة جديدة إلا إذا:
  - خفضت كودًا معقدًا بشكل واضح
  - أو حسّنت الأمان/الجودة
  - أو أزالت منطقًا مكررًا ومتعبًا

- مراجعة `npm outdated` أسبوعيًا.
- أي تحديث رئيسي Major يجب أن يمر في فرع منفصل مع اختبار كامل.

## 8. معايير الجودة والمقاييس

### 8.1 معايير إلزامية

- `npm run lint` ناجح
- `npm run test:ci` ناجح
- `npm run build` ناجح
- `npm run audit` بلا ثغرات حرجة أو عالية

### 8.2 مقاييس قابلة للقياس

- تغطية الاختبارات:
  - Statements: `>= 75%`
  - Branches: `>= 75%`
  - Functions: `>= 85%`
  - Lines: `>= 80%`

- حجم الملفات:
  - ملفات الواجهة: أقل من `200` سطر
  - ملفات CSS العامة: أقل من `250` سطر
  - ملفات المنطق: أقل من `150` سطر

- العيوب:
  - صفر أخطاء lint
  - صفر أخطاء build
  - صفر فشل اختبارات في خط الدمج

### 8.3 مراجعات الكود

- كل تعديل يجب أن يراجع على 3 محاور:
  - صحة السلوك
  - أثره البنيوي
  - أثره على الاختبارات والتوثيق
